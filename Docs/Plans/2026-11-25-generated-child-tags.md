# Generated child tags (runtime) with optional stored overrides — plan

Date: 2026-11-25. Status: **approved by Nico, implemented** (headless harness 76/76; GUI not tested).
Follows: `2026-11-24-folder-tag-scopes.md` (1c "each subfolder gets its own tag").

## Goal
The child tags of a 1c rule are no longer stored in the DB by default. They are generated from the rule's direct
subfolders when the cache is built. A child tag is only stored when the user customises it (rename, aliases,
short code, colour, icon, description), assigns it somewhere, or deletes it. A stored one replaces the generated
one for its subfolder.

### Decisions (Nico, 2026-11-25)
- Generated by default; stored only when the user needs to adjust one ("most are fine automatic").
- Stored overrides are matched to their subfolder by full path. Renamed folders lose their override (it stays as an
  orphaned stored tag); rename detection comes later.
- Meta tags (tags on tags) are wanted, but as a separate feature (see Out of scope). This plan makes sure every
  child tag can become a real stored tag, which meta tags will need.

## Data model
- **Parent tag:** a normal stored tag the rule points to (`TagAssignments.AutoRuleParentTagId`), unchanged.
- **Generated child tag (runtime only):** one per direct subfolder of the rule's folder. Name = folder name,
  colour/icon = parent's, Parent = parent tag, `IsGenerated = true`, `AutoSourcePath` = subfolder path. Gets a
  temporary negative Id, stable for the session (dictionary path → id), so filters and badges work as before.
- **Stored override:** a normal `Tags` row with `ParentId` = parent tag and new column `AutoSourcePath`
  (varchar 2048, nullable; no index, lookups go through the in-memory cache) = subfolder path. If it exists for a subfolder (case-insensitive path), it is
  used instead of the generated tag.
- **Hidden subfolder:** a stored override with `IsArchived = true` (existing column): that subfolder gets no child
  tag.
- **Orphaned override:** a stored override whose path matches no subfolder of an active rule (folder renamed or
  deleted, rule removed). It stays a normal stored tag, marked in the Tags tab ("folder not found"), and re-attaches
  if the folder/rule comes back.

## Behaviour
- **Becomes stored:** editing a generated tag in the Tags tab and saving; dropping/assigning it on any item
  (an assignment needs a real Id); deleting it (stored as hidden). The cached `Tag` object is updated in place
  (Id, IsGenerated), so filter chips and badges that hold it keep working.
- **Tags tab:**
  - Lists stored tags plus generated child tags.
  - Generated tags are shown in italics (the current style).
  - "Show auto-created tags" hides or shows all child tags of rules (generated and stored overrides).
  - Stored overrides get a "Reset to generated" button, which deletes the row; hidden ones (archived) are listed
    struck through so they can be reset.
- **Removing or changing a rule:** generated tags just disappear. No prompts, and the "delete child tags?" dialog
  is removed. Stored overrides stay (they keep their customisation in case the rule comes back).
- **Deleting the parent tag:** as now, deletes its stored children (overrides included) and archives its
  assignments.

## Migration `AddedAutoSourcePathToTag` (replaces the uncommitted `AddedIsAutoCreatedToTag`)
1. Back up, roll back `AddedIsAutoCreatedToTag` (`dotnet ef database update AddedAutoRuleParentTagId`), remove it.
2. New migration: add `AutoSourcePath` + index. Data step for existing auto tags (`ParentId` set, description
   `Auto: <path>`): uncustomised ones (name = last path segment, no aliases, no short code, parent's colour and
   icon, not used by any active assignment) are deleted; the rest keep their row with `AutoSourcePath` = path.
   On Nico's DB that's expected to delete all 16 "Project" child tags (checked with SQL before applying).

## Acceptance (headless harness against a DB copy; GUI only where Nico wants it)
1. A rule's subfolders get generated tags with nothing written to `Tags`.
2. Filters (include/exclude), badges and details pane work with generated tags as before.
3. Renaming a generated tag in the Tags tab stores exactly one row (ParentId, AutoSourcePath); after a rebuild that
   subfolder shows the new name, the others stay generated.
4. Dropping a generated tag on any item stores it once and creates the assignment.
5. Deleting a generated tag hides it (archived row); "Reset to generated" brings it back.
6. Removing the rule leaves no generated tags and no prompts; overrides remain; re-adding the rule re-attaches them.
7. Renaming a subfolder on disk: new generated tag appears, old override shows as orphaned.
8. Migration: existing uncustomised auto tags deleted, customised/assigned ones kept with their path.
9. A new tag created in the Tags tab appears once (duplicate fix).
10. Build: 0 errors, no new warnings.

- Grouping child tags under their parent in the filter panel.
